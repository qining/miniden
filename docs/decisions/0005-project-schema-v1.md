# 0005. Project 文档 = id 寻址 JSON（schema v1）

- 日期：2026-07-17
- 状态：已接受（本次户型扩展的地基，迁移风险排序第一）

## 背景

现状数据模型：内置户型硬编码为 `WALLS/FIXED/DOORS` 常量数组
（墙 = `W(x1,y1,x2,y2,'w'|'g')` 段，门 = `DR(...)`），
用户编辑走 `USERGEO` 的**数组下标覆盖**（`ovW/ovD/hiddenW...`
按索引寻址）+ 用户新增条目。两个致命问题：

1. **索引错位地雷**（AGENTS §1.2）：往 WALLS 中间插一段墙，
   所有用户的覆盖数据整体错位，曾专门把 `GEO_VERSION` 与
   `USERGEO_VERSION` 解耦来止损（代价是 bump 时清空用户数据）
2. **窗户不是一等实体**：现状是墙链里的 `'g'` 子段，
   窗台/过梁高度全局写死（0.67m / 2.25m），款式不可区分，
   无法支持「选墙放窗 + 属性面板」的产品需求

## 决策

把户型重构成 **Project 文档**（完整 schema 见
`design/floorplan-input-and-eng-audit.md` §3.2）：

- 每个实体带**稳定 id**（`w01`/`d01`/`n01`…），门/窗通过
  `wallId + pos(0..1)` 引用所属墙，彻底废除索引覆盖层
- **窗户升格一等实体**：位置/宽度/窗台/过梁/款式/框色/玻璃
- 几何走原语集（ADR-0002）：seg / arc / polygon
- JSON Schema + 版本迁移链：`validate(doc)` 载入时跑，
  `migrate(doc)` 按 `schema` 版本号升级；
  现有 `planner_v1`/`planner_userGeo_v1` 数据做**一次性迁移**
- 内部单位沿用英尺（显示换算走 `fmtLen`，现状不变）；
  文档级字段含 `ceilingH`（层高）与 `northRotation`（朝向）——
  酷家乐「生成后必设/校验」的两项

## 后果

- 解锁全部后续功能（窗户、DXF/PDF 导入、环境预设、多户型）
- 消除索引错位地雷（不可逆的架构改进）
- `eff*()` 几何出口改读文档，2D/3D 继续共用同一份数据
  （AGENTS §7 数据流不变，只是源头从常量+覆盖变成文档）
- 迁移风险最高的一项，所以排 roadmap 第一步（S1）
