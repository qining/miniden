# R8. 家具库 scalability（275 件 → 1000+ 件的增长模型）

日期：2026-09（研究）· 数据全部来自 2026-09 实测（t_3d 65/65 绿）

## 1. 现状基线（实测）

| 维度 | 数值 | 备注 |
|---|---|---|
| 目录条目 | **275** | 76KB 纯数据，**276B/条** |
| 模型函数 | **131**（distinct） | 327KB，**平均 2.5KB/个**（中位 41 行，p90 93 行，max 254 行/tobias） |
| 条目↔模型 | 257 条目引用专属模型，**36 个模型被多条目共享**（figgy×19、sapiens-apple×16、sapiens-cherry×12、epickidz12×10、kiddiecouch×9…），18 条目走 kind 通用回退 | 配色变体 = 同 model 不同 color，**这是免费的** |
| 渲染负载 | **平均 5,762 三角/件**；最重 RÅSKOG 39,404、ORFJALL 36,615 | t_3d `catalog-tri-avg/max` 断言守着 |
| 全场景 | D 布局 52 件 ≈ 246k 三角 / 31 灯（M2 上 PT 精细档 398s） | AGENTS §5.5 实测 |
| 缩略图 | 320×240 独立 WebGL 渲 + 缓存 + IntersectionObserver | 17 张缓存断言 |
| 文件总重 | 产物 ≈1.35MB（three 608KB 占近半） | 双击即开无压力 |

## 2. 增长成本模型（每件新增的边际成本）

| 新增类型 | 数据成本 | 代码成本 | 渲染成本 |
|---|---|---|---|
| **已有家族的配色变体**（如 KALLAX 新色） | +0.3KB | **0** | 0（同模型） |
| 同 kind 的简单件（走通用回退） | +0.3KB | 0 | ~2k 三角 |
| **专属新模型**（中位水平） | +0.3KB | **+2.5KB** | ~5.7k 三角 |
| 专属重型件（playset 类） | +0.3KB | +5-13KB | 6-40k 三角 |

**结论一：目录的增长瓶颈不在数据（76KB/275 条，1000 条才 280KB），
而在①模型代码②3D GPU 负载。**

## 3. 四个真实瓶颈与对策

### 3.1 单文件体积（软顶 ~3-5MB）

- 现状 1.35MB。模型代码线性增长：+500 个专属模型 ≈ +1.3MB
  → **~1,000-1,500 条目（含新家族）时产物触 3-5MB 区间**
  （浏览器双击打开毫无压力；真正的体验底线是加载 <1s——本地文件 5MB 瞬时）
- **超出后的三级方案**（按「单文件灵魂」损伤程度递增）：
  1. **目录扩展包**（推荐）：`catalog-pack.{json,js}` 独立文件，
     「导入目录包」按钮加载（file input / fetch），核心文件不动。
     单文件核心（户型+渲染+基础目录）+ 可插拔商品库 = 既守 ADR-0004
     又解锁 10k+ 量级
  2. GLB 扩展包（懒加载，联网/本地均可）：破坏「离线单文件」的部分承诺
  3. 托管目录 fetch（纯云目录，彻底放弃离线）——**不推荐**
- **数据/代码分离是前提**（R7 `data/catalog.json` + `models-index.json`）：
  条目数据（276B/条）与模型行为（2.5KB/族）解耦后，扩展包只装需要的部分

### 3.2 3D GPU 负载（**先于文件触顶的硬瓶颈**）

- 平均 5.7k 三角/件：30 件客厅 ≈ 170k，52 件 ≈ 246k（M2 已实测）；
  集成的低端 GPU / 手机在 150k+ 时 dollhouse 视角开始掉帧
- **对策（按性价比排序）**：
  1. **视角分级细节**：dollhouse（远）用简化 pass（隐去 <5cm 细节件、
     贴图降档），fp（近）全细节——同一模型注册两个 LOD 档，
     `furn3D(spec, lod)`；断言加 `catalog-tri-avg-low`
  2. **重复构件实例化**（AGENTS §11 已列）：KALLAX 隔板、婴儿床栏杆、
     窗棂——`InstancedMesh`，顶 10k+ 重复三角
  3. **单件预算门禁**（把 t_3d 断言升级成策略）：
     **hard cap 40k 三角/件，warn 20k**；超标件必须在 note 里声明理由
     （RÅSKOG 39k = 密集线材，允许；新件不许默认超标）
  4. 视锥剔除/房间分组合并（§11 已列，场景大后再做）

### 3.3 目录 UI（275 → 1000+ 卡片）

- 现状卡片网格 + 缩略图按需渲：275 没问题；1000+ 时：
  - **虚拟滚动**（只渲可视行；IntersectionObserver 升级成窗口池）
  - 缩略图降 256×192 + 分级（列表用小图，点击进详情再渲大图）
  - 搜索：foldText 线性扫描 1000 条约 1ms，5000 以内不用优化；
    超过再建 ASCII 倒排索引
- 分类：20 类 × 平均 14 件；新增到 30-40 类时**两级目录**
  （大类→子类，`CAT_ORDER` 已支持嵌套数组，数据结构先留好）

### 3.4 仓库卫生（**新发现**：work/ = 644MB 已入库）

- `git ls-files work/` = **1,141 个文件 / 644MB**（参考图 + 历次 check_*.png
  + 截图），.git 对象库因此膨胀（clone 慢、推送慢）
- **建议（E 系列新工作项 E16）**：
  - `work/ref/`（参考图，AGENTS 要求的 source of truth）**保留入库**
  - `work/` 下的**过程产物**（check_*.png、tv_*.png、t_*.html 的旧版本、
    /tmp 拷贝）移出跟踪或转 Git LFS；测试台 html 保留（小而关键）
  - 政策写进 AGENTS：「check 图只在条目 active 期间保留，交付后清理」

## 4. 规模路线图（结论）

| 规模 | 形态 | 需要的前置 |
|---|---|---|
| **275 → 500**（近期） | 单文件直上（产物 ~2MB） | 无（现有架构直接容纳） |
| **500 → 1,500** | 单文件 + LOD 分级 + 实例化 | R7 模块化（data/models 分离）+ §3.2 三项 |
| **1,500 → 10k+** | 核心单文件 + **目录扩展包**（可插拔 json/js） | 扩展包格式规范 + 导入 UX |
