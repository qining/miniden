# R10. UI 改动的验收标准

日期：2026-09（研究/规范）· 配套 R9（风格）· 落地时并入 AGENTS.md
**v2（2026-09-17，用户指出后增补）**：新增两关——**D 交互流程**（先点什么、再点什么、
发生什么，流程设计合不合理）与 **E 人眼可见性**（agent 说「能看到」≠ 人真的看得到）。
这两关是 agent 做 UI 验收时最容易自欺的地方。

**核心问题**：现有门禁（calib md5 / 208 断言）守的是**几何与行为**，
UI 的「看起来对不对」「用起来对不对」没有机器门禁——改坏了只能靠人眼。
本文件把 UI 验收做成**可重复执行的流程**。

## 1. 七道验收关（每次 UI 改动全跑）

### 关 A：行为断言（已有体系，扩展）

- 重新生成三测试台 → t3d 65 / walledit 111 / tpt 32 全绿
- **新 UI 表面必须加断言**（沿用合成 PointerEvent 手法，AGENTS §3）：
  例：新按钮 → 断言点击后某 DOM 状态/属性变化可观察；新面板 → 断言展开/收起
- 断言里**不写死颜色常量**（AGENTS §3 教训）——UI 断言只断言结构/状态/几何

### 关 B：calib 不变性（自动）

- `#calib` md5 必须仍是 `1ac26921871db50ef1c055674c10e6e7`
- `body.calib` 锁死旧布局（§5.4.6）→ UI 重构原则上**不可能**影响 calib；
  如果它变了，说明锁被破坏，**立即停**，不是更新基线

### 关 C：黄金截图（新建）

**`#ui` hash 模式**（新加）：进入指定规范化 UI 状态并冻结（隐藏光标/时间戳/
随机元素），供 headless 截图比对。

首批黄金集（`work/golden/`）：

| 状态 | hash | 覆盖 |
|---|---|---|
| 2D 默认（空布局，目录展开） | `#ui:2d` | 顶栏/左右面板/2D 画布 |
| 2D + 选中一件家具 | `#ui:2d-sel` | 属性面板填充态 |
| 3D 俯瞰 / 3D 室内 | `#ui:3d` / `#ui:fp` | 3D 画布 + 视图专属控件 |
| 夜间模式 / 英尺单位 / 面板全收起 / 光追对话框 | `#ui:night` `#ui:ft` `#ui:collapsed` `#ui:dlg` | |

**比对规则**：
- **本地**：像素 diff 比例 ≤0.3% 为 PASS；超限输出 diff 图（差异像素标红）供目检
- **CI（ubuntu-latest + Chrome）**：同代码两次渲染 md5 必须一致（确定性）；
  黄金基线用 CI 环境生成
- **改样式的 PR**：必须重拍受影响状态的黄金图并**贴新旧对比**——
  黄金图更新是显式动作，不是默认通过

### 关 D：交互流程（**v2 新增**——agent 验收的头号盲区）

**验的不是「每个按钮都能点」，而是「用户按『先点 A → 再点 B → 然后发生 C』
走完整流程时，每一步都有它该有的一切，而且这个流程的设计站得住」。**

#### D.1 流程脚本（每个新增/修改的流程的必交产物）

```
任务：<一句话目标，如「加一张沙发并挪进卧室」>
 1. 点搜索框     → 期望：光标 + focus 环
 2. 输入「沙发」 → 期望：卡片实时过滤（断言：可见卡片数变化）
 3. 点卡片       → 期望：家具出现在画布 + 选中框（断言：DOM + 截图）
 4. 拖拽         → 期望：实时跟随 + 尺寸标注跟随 + 吸附提示
 5. 松手         → 期望：落位 + 选中保持 + 采购清单 +1
 6. 点旋转手柄→拖 30° → 期望：2D 图例旋转 + 属性面板角度显示 30°
 7. Delete       → 期望：删除 + 清单 -1 + 可撤销
失败路径（至少 2 条）：
 F1 拖到与其他家具重叠 → 红色描边（已有）+ 提示
 F2 属性面板输入非法值 → 行内报错（为什么+怎么改），不是 alert、不是静默
```

**执行**：整段脚本在测试台用合成 PointerEvent 跑（AGENTS §3 手法）。
**每一步**断言两样：(a) **状态变化**（数据层）+ (b) **用户可见反馈**
（DOM 层：class/文字/计数/可见性）。

**反馈缺口规则**：一个用户动作之后**零可见反馈** = **设计缺陷**，
不是「测试跳过」。时间参考（HCI 经典值）：可见反馈 ≤300ms；
300ms–1s 期间必须有进行指示；>1s 必须有进度 + 可取消。

#### D.2 HCI 评审清单（实现前过一遍；PR 里逐条回答）

| 维度 | 问什么 | 常见违规 |
|---|---|---|
| **对象贴合（最高）** | 一个从未看过本软件、没读任何文档的 homeowner 能完成吗？ | 主路径藏在 pro 操作后面；行业术语（CAD 词/工程词）；ADR-0006 |
| 步数 | 从目标到完成几步？每步都必需吗？ | 对可撤销操作弹确认框 |
| 直接操纵 | 能不能「直接操作对象」而不是「先进模式」？ | 工具模式滥用 → 模式混淆 |
| 模式可见 | 模式激活时界面持续显示（按钮按压态/横幅）？Esc/再点可退出？ | 「我在加墙模式里出不来」 |
| 可发现性 | 不看文档能找到吗？位置/标签/分组？ | 主操作藏在次要位置 |
| 注意力 | 一屏只有一个主操作吗？ | 三个高亮按钮互相竞争 |
| 选择负荷（Hicks 定律） | 同屏选择项多少？高级选项折叠了吗？ | 3 个选项做成 20 项下拉 |
| 错误处理 | 非法操作：说明原因 + 给修复路径？ | 静默 / 只有一个红叉 |
| 一致性 | 同一手势处处同义？（拖=移；转只靠手柄） | 有时拖拽是旋转 |
| 精度辅助 | 精密操作（cm/0.1°）有缩放+吸附+数字读数？ | 精度活没读数（我们已有——保持） |
| 目标尺寸（Fitts） | 常用目标大且近？最小可点目标 ≥24px？ | 缩远后细手柄点不中 |

#### D.3 流程回归（量化）

为核心流程建「基准任务脚本」（加家具 / 画墙 / 放窗 / 开关灯 / 跑光追），
每个记录**完成所需动作数 + 反馈步数**。新特性落地时全跑一遍：
**基准任务的动作数涨了而无用户收益 = 回归**（机器可断言：数 dispatch 次数）。

### 关 E：人眼可见性验证（**v2 新增**——「agent 说能看到」≠「人看得到」）

**失效模式**（agent 经典自欺）：用 DOM 查询验证（`querySelector` 找得到、
`textContent` 正确、`display` 不是 none）就报告「已显示/可见」，
但人**实际看不见**——因为它被别的元素盖住（z-index）、
在可视区外（折叠的面板里/滚动区外/父容器 overflow 裁掉）、
opacity 为 0、字号小成一点、颜色与背景几乎相同、
或者只存在于一个**已经自动关闭**的中间态。

**规则：任何「可见」声称必须过三层探针。DOM 存在不是可见的证据。**

| 层 | 探针 | 通过标准 |
|---|---|---|
| ① 几何 | `getBoundingClientRect()` | 在视口内**且**在所有祖先滚动/裁剪容器的可视范围内；面积 ≥8×8px |
| ② 遮挡 | `document.elementFromPoint(中心点)` | 命中的是目标本身或其**后代**（目标在该点是**最上层**）——AGENTS §3 真实命中测试手法的反向用法 |
| ③ 感知 | **截图 → 裁目标区域 ≥2× 放大 → Read 看图** | 人眼真的看得见且可读；文字与背景对比度 ≥ WCAG 4.5:1（大字 3:1） |

- **第 ③ 层不可省略**：不允许只凭 DOM 下「可见」结论；截图必须是**最终状态**
  （不是瞬态），且裁剪范围足够大（AGENTS §4.4：小裁剪会误判，扩大再看）
- 任一层失败 = 真 bug（修 z/布局/对比度）；「用户滚动就能看到」**不算**
  首屏可见声称的通过——滚动位置本身也是验收的一部分
- 这一关是 AGENTS §10「用户圈图指出问题时先放大裁剪确认」的**反向**：
  那条是「人说看到了，agent 放大确认」；这条是「agent 说看到了，
  （模拟）人眼截图确认」——同一套放大裁剪技术，双向使用
- 典型陷阱清单：元素在 `display:none` 的面板里但 `visibility` 未设 /
  透明遮罩盖在上面使 `elementFromPoint` 返回 `<body>` / 暗色模式下白字白底 /
  toast 自动关闭后 agent 才截图 / headless 1× 截图里 10px 字糊成一团

### 关 F：交互体检（手动，~2 分钟，固定清单）

- [ ] 键盘：Tab 走完整控件环，focus 环可见，Esc 关对话框/取消操作
- [ ] 三视图 × 双单位 × 日夜 = 12 个组合各瞟一眼（文字不溢出、数字
      tabular 对齐、accent 一致）
- [ ] 面板拖宽/收起/刷新后恢复（`planner_panels_v1`）
- [ ] 拖家具时顶栏/工具条**不跳动**（定高单行规矩，AGENTS §5.2）
- [ ] 静止时 GPU 占用 ≈0（按需渲染没被破坏）
- [ ] **手感**（合成事件替代不了）：拖拽跟手度、吸附的「咔哒」感、
      旋转手柄在目标上的手感

### 关 G：卫生（自动可查）

- [ ] `node --check` 通过；`window.__ERRS` 空（console error/warn 全收）
- [ ] **文件体积预算**：UI 小功能 ≤5KB；超了要说明
- [ ] **token 纪律**：新增 CSS 不得出现 token 之外的裸色值/裸 px
      （脚本查：CSS 区 hex 值 ∉ token 集合 → 列清单）
- [ ] 中文文案不写死宽度；新文案同时想 zh 表达

## 2. 用户报「UI 不对/看不见」的处理流（AGENTS §10 扩展）

1. **先放大裁剪确认双方看到的是同一处**（§10）——用户说「看不见 X」，
   第一步不是改代码，是截最终状态 + 放大 X 区域，确认自己确实看不到
2. 复现 → 归因（关 E 三层探针逐层查：几何？遮挡？对比度？瞬态？）
3. 修复 → 跑七道关
4. **沉淀**：暴露通用规律 → 自我生长四步写进 SKILL/AGENTS + 本文

## 3. 明确「不验收」的（避免过度工程）

- 跨浏览器像素一致（只保 Chrome；其他浏览器行为级可用即可）
- 响应式/移动端（v1 桌面工具；<1000px 给「请用大屏」提示）
- 动画逐帧（只验收**起止状态**进黄金集，过程人眼）
- a11y 完整审计（v1 做关 F 键盘项；WCAG 全项归 v2）

## 4. 落地工作量估计

- 关 C：`#ui` hash 模式 + 截图/diff 脚本（PIL 或页面内 canvas）+ 8 张基线 ≈ 1 天
- 关 D：零新基建——测试台 dispatch 手法现成；先给 5 个核心流程写基准脚本 ≈ 半天
- 关 E：零新基建——`elementFromPoint`（现成）+ 截图裁剪（现成）；
  写一个 `visibleToHuman(el)` 三合一探针函数即可复用
